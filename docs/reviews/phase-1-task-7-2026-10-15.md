# Review: Task 7 hardening, commit 68f624d (+ log 77fa559)

**Verdict: blocked** on two items. The seven hardenings themselves are correct and the mutation checks are
real: the FIFO swap, the unlistable directory, the store-failure abort, the subtree `LIKE` collision, the
mtime distance, the probe failure and the mount boundary all do what the plan says. But the same refactor
that moved hashing inside the scan row broke `files_hashed`, and "an unreadable directory is not a deleted
one" was only half-implemented: the root listing and a single unreadable file still retire their rows.

Everything here is from the code, the tests and a read-only look at the live catalogue. No real root was
scanned for this review.

## What is correct

- Safe opens go through one door (`open.ts`): `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`, then `fstat`, then
  refuse anything that is not a regular file. The FIFO-swap test's timeout is the assertion.
- A store failure aborts the scan with `status = 'failed'` and a named `failure_stage`, instead of becoming
  one more per-file row.
- The three subtree functions use `substr(rel_path, 1, length(@relPath) + 1) = @relPath || '/'`, so
  `files/` no longer claims a sibling `Files/`.
- `identity.ts` compares `|a − b| < 2 s` rather than bucketing, and the straddling case is pinned.
- `VolumeProbe` returns `found | absent | failed`; `probe_failed` survives the `scan_roots` status CHECK via
  the rebuild migration; report and stats show it.
- The walk is split from the lifecycle (`scan-root.ts` / `scanner.ts`), which is the right seam. It is at
  397 lines and should be split further while it is next touched.

## Blockers

1. **`scans.files_hashed` records 0 on every real scan.** The plan change that runs hashing as a stage
   *inside* the scan row is right, but `finishScan` still writes the column from the walk's totals:
   `store.ts:154` passes `totals.filesHashed`, and the walk never sets it (`scanner.ts:104` initialises it to
   `0` and nothing increments it). The hash stage writes the real figure itself
   (`dedupe.ts:196` → `setFilesHashed`), and then `finishScan` overwrites it with the walk's zero. Before
   Task 7 the CLI ran `computeHashes` *after* the scan had finished, so the column survived; now the scan
   closes last and every scan records 0.
   *Repro:* run `scan()` with `computeHashes` as its `hash` stage on files that need hashing, then read
   `scans.files_hashed` and `summary.md`. Both say 0. Task 6's run reported `15,418 hashed`, so this is a
   regression introduced by Task 7.
   *Smallest fix:* make the hash stage the only writer. Drop `files_hashed` from `finishScan` (and the dead
   `filesHashed` field from `ScanTotals`), so `setFilesHashed` is the one place that sets it.

2. **Unreadable is not yet "not deleted".** Task 7 taught `markMissingNotSeen` to spare the subtree of an
   unlistable directory (`store.ts:290-314`), but two holes remain:
   a. **The root listing.** When the walk cannot list the root itself it records the error for `relPath = ''`
      and pushes `''` into `unlistableRelPaths` (`scan-root.ts:253`). The protection SQL then tests
      `substr(rel_path, 1, length('') + 1) = '' || '/'`, i.e. `substr(rel_path, 1, 1) = '/'`, which matches
      nothing: every item below the top level is marked `missing` while the walk in fact saw nothing at all.
   b. **A single unreadable file.** A file whose `lstat` or head-read fails with anything other than `ENOENT`
      is recorded as an error and then dropped (`scan-root.ts:341-353`) — no row is upserted, so its
      `last_seen_scan` stays old and `markMissingNotSeen` retires it. One `EACCES` on one file looks exactly
      like that file being deleted, which is the same bug the directory fix was for.
   c. **The protection list is a variable-count IN list.** `dir_id NOT IN (?, ?, ...)` is built from every
      directory id in the protected subtree. An unreadable directory with thousands of subdirectories would
      exceed SQLite's parameter limit and fail the scan — on exactly the tree the protection is meant to
      save.
   *Smallest fix:* protect by path prefix, not by enumerating directory ids. Treat `''` as "the whole root
   could not be listed, retire nothing", match the rest with a `NOT EXISTS`/`substr` subquery over a single
   `json_each(@protected)` value, and add a file's own `rel_path` to the protected set when its `lstat` or
   head-read fails with a code other than `ENOENT`. Extend `ScanHooks` with `listDirectory` and `openFile`
   seams so the tests can inject those failures and pass as root, since `chmod 000` does not deny root.
